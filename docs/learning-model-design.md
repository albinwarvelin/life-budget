# Proposed learning-model redesign

Status: proposal, not implemented. The source-row ordering change is independent
and is implemented with migration `0008_import_provenance`.

## Problems confirmed in the current implementation

- Screenshot imports try transaction-type scopes in a fixed order. A positive
  amount's first income-category match ends the search before reimbursement
  evidence is evaluated. The supplied example currently gets Salary with
  confidence 1.0 from two income amount-band observations. Evaluating the
  reimbursement scope separately puts Car first with confidence 0.7513.
- A pattern's base weight is applied when learning and again when scoring,
  so its effective per-observation influence is squared. Account observations
  also create global and account patterns that are both counted at prediction.
- Relative score share is displayed as confidence. One weak matching category
  gets 100% even if there is almost no usable evidence.
- Learning events have no transaction identity/revision. Edits append examples
  without withdrawing the old label; deletes do not withdraw examples. Manual
  CRUD updates category learning but does not consistently update the other
  models. Learning failures are logged without a durable retry mechanism.
- Amount features use absolute, coarse bands. They cannot represent a smooth
  distinction between small incoming reimbursements and large income, and
  unrelated personal names do not provide shared full-merchant evidence.

## 1. Make confirmed examples the source of training truth

Keep financial records and the learning store separate. Persist an outbox event
with each financial create/edit/delete in the same financial database commit.
Each event contains a transaction ID, revision, operation, and the reviewed
features/labels required by the learner. Process it locally and idempotently;
retries cannot duplicate training examples. Show outstanding events and the
active model revision so failed synchronization is visible.

The training view has at most one current example per transaction. A correction
replaces that example; deletion withdraws it. Historical audit events remain
immutable. Retrain from this view rather than accumulating pattern weights.
Distinguish explicit corrections from confirmations of a model suggestion so
acceptance bias can be measured; never treat an unapproved suggestion as a label.

Preserve reviewed source direction and currency explicitly. Imported amounts
can be corrected before approval, so an unedited OCR draft is not a substitute
for the final reviewed source amount. For historical rows whose original sign
was not preserved, represent that missing information explicitly rather than
inventing it. Ledger amounts and financial calculations continue using Decimal.

## 2. Use shared, predictive features

Start with normalized merchant/description word TF-IDF and character n-grams,
account/currency indicators, source direction, and smooth amount features such
as splines of log(1 + absolute amount), separately scoped to each currency.
Character fragments help with OCR variation; they do not establish whether a
counterparty is a person.

Include tentative name-shape features (alphabetic token count, digits, business
suffixes) and optionally an explicitly confirmed person/business/unknown label.
These are uncertain features, not a rule that names imply Car. Interaction
features between direction, currency, amount and counterparty shape allow the
learner to discover small personal incoming payments across unseen names.
Avoid hardcoded category names or a special +50 NOK rule.

Descriptions generated by another model must not be passed off as observed
source text. Train and evaluate with the features available at prediction time.

## 3. Fit regularized probabilistic classifiers

Use two pooled multinomial logistic classifiers:

```text
p(type=t | x)         = softmax(a_t · phi(x) + intercept_t)
p(category=c | x, t)  = softmax(b_c · psi(x, t) + intercept_c)
p(type=t, category=c | x) = p(t | x) * p(c | x, t)
p(category=c | x)     = sum_t p(t | x) * p(c | x, t)
```

The type classifier uses observed features, without a predicted category as
input. The category classifier shares evidence across types, with type and
selected type interactions as features. This removes the current circular
dependency and the first-matching-type shortcut. If type is explicitly selected
by the user, condition category suggestions on that value. Otherwise rank joint
type/category alternatives across all types. Category kind remains a label,
consistent with the existing domain rules; do not introduce hard exclusions.

Fit parameters by minimizing penalized cross-entropy:

```text
loss = -sum_i log p(correct_label_i | features_i) + lambda * ||weights||^2
```

The first term penalizes wrong predictions. The second limits memorization of
rare names and correlated features. Choose regularization and any class weighting
using validation rather than assigning another set of hand-tuned signal weights.
Inspect the additive feature contributions to each class's score in the existing
learning UI. These are model explanations, not causal explanations.

scikit-learn would add a local numerical ML dependency (and its NumPy/SciPy
dependencies), with maintained feature pipelines, classifiers and evaluation
tools. No network inference is needed. No dependency is added by this proposal.
Model feature arrays may use approximate numerical representations; they must
never be written back as monetary values or used for ledger calculations.

## 4. Validate uncertainty and improvement before switching

Evaluate on later confirmed import batches, with one current example per
transaction and all preprocessing fitted only on training data. Add a separate
evaluation holding out counterparties to test generalization to new names.
Use confirmation chronology to reflect what the model knew when predicting,
even when historical statements were imported out of date order.

Compare the current model, a simple baseline and the proposed model using macro
F1, per-category recall, top-three accuracy, log loss and calibration plots.
Measure suggestion precision against coverage: choosing fewer confident
suggestions should lower the correction rate. Test unseen names, small
reimbursements, actual salaries, currency isolation, OCR variation, corrections,
deletions and repeated synchronization. A +50 NOK person-like payment must not
be unconditionally assigned Car.

Estimate confidence on held-out data. Calibrate when enough independent examples
exist; with scarce labels, show limited evidence rather than precise certainty.
Choose abstention thresholds and score-margin requirements from validation.
Uncertain predictions should show alternatives or leave fields unselected.

## Delivery sequence

1. Add revisioned confirmed examples, the durable outbox and a safe rebuild from
   current reviewed records. Keep legacy events for audit, outside the new
   training view, because their revisions cannot be reconstructed reliably.
2. Build the shared feature pipeline and the two classifiers; run them alongside
   the current model without replacing active predictions.
3. Add evaluation, explanations and uncertainty handling. Switch model versions
   only after measured improvement; preserve rollback to the previous model.
